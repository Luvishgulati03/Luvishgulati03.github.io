the problem.

Schools want AI to save teachers time. They also need to protect student data and keep teachers in control.

That made the real product questions clear: where answers come from, who sees a student's identity, who approves the output and how data gets deleted. Bose handles those questions in the system design, not through a privacy setting added later.

the architecture.

Bose uses the same core as Henry: memory, retrieval, routing and guardrails. I changed the tools for a school setting and put teachers in control of anything students see.

I built it in this order:

01

airlock first

I built the identity boundary before any teaching feature, so names never entered the rest of the system.

02

the school's own material

Each class searches its own syllabus and answer bank using local embeddings.

03

teach, then test

Tutor mode controls how much help to give. The test site creates, grades and explains each result.

04

hand it to the teacher

Teachers approve student-facing output. They also get grading help, worksheets and grouped doubts.

privacy engineering.

This is Bose's main privacy rule: a student's name never reaches an external model.

The identity airlock. The vault holds the real identity. A scrub step removes personal details before the model sees the question. The answer returns through the airlock.

Four parts enforce the rule:

  • The vaultReal identities stay in one AES-256-GCM encrypted store. The rest of Bose uses a pseudonymous ID.
  • Scrub before savingBose removes identifying details before saving data or calling an external model.
  • On-device proctoringExam mode records browser events. Video never leaves the device.
  • Right to forgetIdentity lives in one vault, so deletion is direct and complete.

What I do not show: school names, student data, private work or the repository. This page covers the public architecture and my product decisions.
